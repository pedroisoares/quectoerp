# ADR-0004: Technology stack

- **Status:** Accepted
- **Date:** 2026-11-16
- **Deciders:** @pedroisoares

## Context

QuectoERP promises small, fast services with a measured resource budget, and a minimal on-premises install of **one binary plus PostgreSQL**. It is developed mostly by one maintainer working with an AI assistant, so the stack has to favor short write-compile-test cycles, a large pool of contributors in Brazil and good libraries for Brazilian tax documents (NF-e and others). The bottleneck of an ERP is the database and I/O, not raw CPU.

A first architecture draft used a conventional .NET stack (JIT, EF Core, an application-level message bus, Keycloak). A later review replaced the heavy pieces so that every service can be compiled ahead of time and stay inside the budget.

## Decision

| Layer | Choice |
| --- | --- |
| Language and runtime | C# on **.NET 10 (LTS)**, compiled with **Native AOT** for every service. The SDK version is pinned in `global.json` |
| Code generation | Source generators instead of runtime reflection: Minimal APIs with the Request Delegate Generator, `System.Text.Json` source generation, SQL mapping generated from metadata |
| Structure | Modular monolith: one project per bounded context, composed into a single host or deployed as separate services with the same contracts |
| Database | **PostgreSQL**, one schema per module. The only mandatory infrastructure |
| Data access | **Npgsql** with SQL generated by the SDK from metadata. No ORM in services |
| Events | Transactional outbox in PostgreSQL with `LISTEN/NOTIFY` in a single process; **NATS JetStream** when there is more than one process |
| Identity | **OpenIddict** embedded in the identity module; external identity providers only through OIDC federation |
| Front end | React and TypeScript, screens generated from metadata in one shell, with a bundle-size budget |
| Tax engine | Rust compiled to WebAssembly, so the same calculation runs on the server, in the browser and at the point of sale. C# stays as the fallback if it does not pay off |
| Observability | OpenTelemetry. The minimal install needs no monitoring backend (JSON logs on stdout and a `/metrics` endpoint) |
| Tests | xUnit, Testcontainers for PostgreSQL, architecture tests for module boundaries |
| CI | GitHub Actions |

Milestone 0.2 (proof of concept) must confirm the risky parts with a real sample module: Native AOT support in OpenIddict, Npgsql and the HTTP stack, the outbox, and the actual numbers against the resource budget. Any piece that fails is replaced through a new ADR that supersedes the relevant line of this one.

## Consequences

- Startup in tens of milliseconds and small binaries make the budget and the "one binary plus PostgreSQL" install realistic.
- Libraries that depend on runtime reflection or dynamic code generation cannot be used in services. This rules out, for example, EF Core at runtime and most reflection-based message buses, and it narrows the choice of third-party packages.
- Generated SQL means the SDK carries more responsibility; it also means the kernel knows every query a module can run.
- Rust adds a second toolchain for one component only. It stays optional until the tax engine starts in Phase 1.
- Every further runtime dependency needs its own ADR with its cost (see ADR-0001).

## Alternatives considered

- **Conventional .NET (JIT, EF Core, Wolverine, Keycloak):** fastest to start, but EF Core and dynamic code generation work poorly with Native AOT, and Keycloak alone needs hundreds of megabytes of memory just for login.
- **Rust for everything:** maximum performance, but very little ready-made for Brazilian tax documents and slower iteration on entity-heavy business code.
- **Java or Kotlin on the JVM:** mature ecosystem, but higher memory at rest, and native compilation adds similar constraints to .NET AOT without the same tooling for our team.
- **RabbitMQ or Kafka from day one:** extra infrastructure that a small install does not need.
